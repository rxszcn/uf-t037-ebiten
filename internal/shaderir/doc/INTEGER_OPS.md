# 整数移位、除法与取模的跨后端语义

本文档说明 Kage 着色器中整数移位（`<<`、`>>`）、除法（`/`）与取模（`%`）为什么
必须在翻译到各图形后端时统一改写，以及前端（`internal/shader`）、中间表示
（`internal/shaderir`）和各后端（`glsl` / `hlsl` / `msl`）各自承担的职责。

## 1. 背景：同一个着色器为什么会渲染出不同像素

Kage 的设计目标是让同一份着色器源码在 OpenGL / OpenGL ES、DirectX、Metal 上得到逐
像素一致的结果。源码先被编译成与后端无关的 `shaderir.Program`，再由三个后端分别翻译
成 GLSL、HLSL、MSL。

问题在于这三种语言对若干整数运算的定义并不相同，而旧的翻译直接把 IR 的
`LeftShift`、`RightShift`、`Div`、`ModOp` 裸发成目标语言的 `<<`、`>>`、`/`、`%`。
于是同一份 IR 在不同驱动、不同 GPU 上会走到不同的硬件行为，产生不一致的像素结果。
位运算粒子效果这类依赖移位计数和位模式的着色器受影响最明显。

## 2. 统一的语义基准：Go

Kage 的语法和运算语义以 Go 为基准（见 `internal/shader` 对 `go/ast`、`go/constant`、
`go/token` 的复用）。因此整数运算的"正确答案"以 Go 语义为准。下表中的结论均由 Go
程序实测确认（int32 宽度，对应着色器里的 `int`）。

| 情形 | Go 行为 |
| --- | --- |
| `x << n` / `x >> n`，`n >= 32` | 结果为 `0`（Go 按 32 位宽度取模后移位） |
| `x << n`，`n < 0` | 运行时 panic：`negative shift amount` |
| 负数右移 | 算术右移（保留符号位），如 `-7 >> 2 == -2` |
| 整数除法 | 向零截断，如 `-7 / 2 == -3`、`7 / -2 == -3` |
| 整数取模 | 余数符号跟随被除数，如 `-7 % 2 == -1`、`7 % -2 == 1` |
| `x / 0`、`x % 0` | 运行时 panic：`integer divide by zero` |
| `INT_MIN / -1` | 不 panic，结果为 `INT_MIN`（有符号溢出回绕） |
| `INT_MIN % -1` | 不 panic，结果为 `0` |

着色器运行在 GPU 上，没有 panic 机制，也无法把异常抛回 Go 侧。因此凡是 Go 在运行时
才暴露的错误（负移位计数、零除数），在着色器里都必须被翻译成一个**定义良好、各后端
一致**的结果，而不是依赖 GPU 的未定义行为。

## 3. 各后端原生语义的差异

### 3.1 移位

- **移位计数宽度**：GLSL、HLSL、MSL 的 32 位移位都只取计数的低 5 位。例如 `x << 33`
  在硬件上等价于 `x << 1`，而 Go 规定结果为 `0`。
- **左移负数**：对负数（符号位为 1）做有符号左移在 GLSL 中是未定义行为；不同编译器
  可能给出不同结果。
- **右移负数**：三种语言对有符号整数右移通常都是算术右移，与 Go 一致，但前提是计数
  合法；越界计数仍未定义。

### 3.2 除法与取模

- **零除数**：GPU 的整数除以零通常产生未定义值或硬件特定值（常见为 `0` 或
  `INT_MIN`），不会报错。
- **`INT_MIN / -1`**：数学结果 `2147483648` 超出 int32 范围，x86 的 `idiv` 会触发陷阱，
  各着色语言编译器对此的处理不一致。Go 明确规定结果为 `INT_MIN`。
- **取模方向**：GLSL 旧版本的 `%` 对整数未定义；HLSL 的 `fmod` 是截断取模，而 GLSL 的
  `mod` 是地板取模。符号约定的差异会让负数取模结果不同。
- **fxc 警告 X3556**：HLSL 编译器对有符号整数 `/` 和 `%` 会发出警告并建议改用无符号
  类型，旧代码只对 `%` 做了规避，`/` 仍裸发。

## 4. 决策：在后端翻译层统一改写，而不是在前端展开

### 4.1 为什么不把运算在前端（`internal/shader`）就展开成等价表达式

- 前端的产物是与后端无关的 IR，需要同时服务 GLSL、HLSL、MSL 三个后端。每种语言表达
  同一件事的语法不同（HLSL 用宏、MSL 用模板、GLSL 用重载函数），在 IR 层硬编码某一种
  写法会污染其他后端。
- 前端只负责**编译期可判定**的校验与常量折叠（见 4.2），把运行时才知道取值的运算保留
  为 IR 操作码，由最了解目标语言能力的后端决定如何安全落地。
- 复用已有的 `modInt` 模式：三个后端原本就有为取模准备的 helper / 宏，本次改造沿同一
  模式补齐除法和移位，改动集中、易于审计。

### 4.2 前端（`internal/shader`）的职责

前端不生成 helper，只做编译期能确定的事：

- **常量折叠**：两个操作数都是常量时，用 `go/constant` 直接按 Go 语义算出结果
  （`expr.go` 的 `BinaryExpr` 分支）。
- **常量移位计数校验**：常量移位计数为负或超过 `maxConstShift`（`1 << 16`）时编译报错
  （`expr.go` 的 `shiftCount`）。
- **常量零除数报错**：除数是常量 `0` 时直接报 `division by zero`。
- **非常量情形保持原样**：移位计数或除数是变量时，前端无法判定取值，保留为 IR 的
  `LeftShift` / `RightShift` / `Div` / `ModOp`，交给后端 helper 兜底。这与既有测试
  （`TestCompileShiftCountWithVariable`）允许变量移位的约定一致。

### 4.3 中间表示（`internal/shaderir`）的职责

- 操作码语义不变，仍是与后端无关的 `Div`、`ModOp`、`LeftShift`、`RightShift`。
- 新增 `Program.ExprType`（`type.go`），在给定 block 作用域内推导任意表达式的具体类型。
  后端用它判断一个 `Div` 的操作数是整数（需要改写）还是浮点 / 矩阵（保留原生 `/`）。
  类型规则集中在 `check.go` 的 `TypeFromBinaryOp`，`ExprType` 复用这些规则，避免在三个
  后端各写一份类型推导。

### 4.4 后端（`glsl` / `hlsl` / `msl`）的职责

每个后端在 `Binary` 表达式分发处做同一套改写，并在 prelude 中提供对应 helper：

| IR 操作码 | 改写目标（三后端同名） | 作用 |
| --- | --- | --- |
| `LeftShift` | `shiftLeftInt(x, count)` | 计数夹到 `[0, 32]`，经无符号类型左移 |
| `RightShift` | `shiftRightInt(x, count)` | 计数夹到 `[0, 32]`，保留有符号算术右移 |
| `Div`（整数） | `divInt(x, y)` | 零除数返回 0；`INT_MIN / -1` 返回 `INT_MIN` |
| `ModOp` | `modInt(x, y)` | 建立在 `divInt` 上的截断取模 |
| `Div`（浮点 / 矩阵） | 原生 `/` | 不经过 helper |

各语言的落地方式：

- **GLSL**（`glsl/glsl.go`）：在 `utilFunctions` 中提供标量与 `ivec2/3/4` 的重载函数，
  覆盖标量除数与逐分量除数两种形态。左移先转 `uint` / `uvec` 再移位后转回，规避负数
  左移的未定义行为。helper 同时注入 `GLSLVersionDefault`（桌面）与
  `GLSLVersionES300`（移动 / WebGL2）两个版本。
- **HLSL**（`hlsl/hlsl.go`）：沿用 `#define` 宏形式（原因见源码注释 #3356：部分编译器
  无法按向量宽度解析重载）。`divInt` 用三元表达式处理零除数与 `INT_MIN / -1`，移位用
  `asuint` / `asint` 与 `clamp`，标量和向量参数都适用。
- **MSL**（`msl/msl.go`）：用 `template<int N>` 覆盖 `vec<int, N>`，配合标量重载。
  左移用 `as_type<uint>`，计数用 `min` / `max` / `clamp` 夹取。

### 4.5 为什么统一把计数夹到 `[0, 32]`、把零除数定义为 0

- **移位夹取**：Go 规定计数达到类型宽度（32）结果即为 0。把计数夹到不超过 32，再用
  无符号移位，`count >= 32` 时移 32 位自然得到 0；负数计数夹到 0 后等价于不移位。这样
  无需分支即可在所有后端得到与 Go 一致的定义良好结果，同时天然吸收了前端无法拦截的
  运行时负计数。
- **零除数返回 0**：GPU 无法 panic，必须选一个确定值。选择 0 是因为多数 GPU 整数除以
  零的硬件结果本就趋近 0，且 0 是中性、可预测的值；文档与测试都明确这是着色器侧的
  定义，而非 Go 的 panic 语义。
- **`INT_MIN / -1` 返回 `INT_MIN`、`INT_MIN % -1` 返回 0**：直接对齐 Go 的明确规定，
  绕开硬件溢出陷阱。`modInt` 统一建立在 `divInt` 之上，因此取模在这两个边界也自动
  正确，不再出现旧 HLSL 宏里 `abs(INT_MIN)` 溢出的问题。
- **可移植的 INT_MIN 字面量**：helper 中统一写作 `(-2147483647 - 1)` 而不是
  `-2147483648`，因为后者在部分编译器里是"一元负号作用于正字面量 2147483648"，而该
  正值超出 int32 会先溢出。

## 5. 测试策略

跨后端一致性无法靠单一后端的快照测试保证，因此测试分两层：

- **IR 层**（`internal/shaderir/ir_test.go` 的 `TestExprType`）：验证 `ExprType` 对常量、
  局部变量、整数 / 浮点除法、移位、一元与嵌套表达式的类型推导，确保后端判断"是否整数
  运算"的依据可靠。
- **端到端翻译层**（`internal/shader/integer_ops_test.go`）：用一份覆盖变量移位、越界
  计数、负数右移、截断除法取模、`INT_MIN` 边界、零除数、标量 / 向量组合、浮点除法的
  着色器，编译到全部后端（GLSL 桌面、GLSL ES300、HLSL、MSL），断言：
  - 用户代码中不出现裸的 `<<` / `>>`（必须走 helper）；
  - 每个后端都定义并调用了 `shiftLeftInt` / `shiftRightInt` / `divInt` / `modInt`；
  - 浮点除法仍保留原生 `/`，不被误改写。
- 既有的 `internal/shader/testdata` 快照测试继续覆盖翻译文本；其中内嵌完整 prelude 的
  `for_range` / `for_range_array` 期望文件随 prelude 扩展同步更新，函数体保持不变。

## 6. 未覆盖范围与后续事项

- `internal/shaderir/pssl` 目前是未实现的桩（`Compile` 直接 panic），本次未为其添加
  helper；将来实现 PSSL 后端时应套用同一套 helper 命名与改写规则。
- 本测试验证的是"翻译到各后端的源码都走了语义一致的 helper"，不在 CI 中实际运行 GPU
  着色器比对像素。如需更强保证，可在具备对应硬件的环境补充渲染回读测试。
